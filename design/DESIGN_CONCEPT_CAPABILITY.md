# 首頁首屏能力可讀化規格

## 0. 目標與設計結論

本輪只解一個問題：讓第一次進站的招募者或潛在客戶，在 **5 秒內說得出 Zorya 能處理哪些工作**。

保留首頁 v3「把混亂變成路徑」的主標、雙欄構圖與 voxel hero；不另做一套視覺語言。改動集中在 hero 文案層級：

1. 保留有辨識度的理念主標。
2. 以具體副標說清楚工作範圍與交付形式。
3. 將目前的 availability pill 改成狀態標籤，不再讓它兼任能力說明。
4. 在副標下加入可掃讀、可點擊的「我能做什麼」能力帶，每項直接連到案例或 Demo 證據。

能力帶不是技能關鍵字牆，而是一組「動作＋證據」入口。訪客先看到能做什麼，再自行選擇是否深入案例。

---

## 1. 診斷：5 秒內必須帶走的三件事

### 1.1 她是解決哪一類問題的人

> 她能把模糊的商業需求、散亂資料與卡住的流程，整理成可執行的路徑。

目前的主標能傳達方法與態度，但「問題」與「交付物」都過於抽象；只看首屏，可能被理解成顧問、PM、分析師或設計師，無法快速定位。

### 1.2 她具體能做哪些工作

> 需求釐清、資料整併與異常分析、規則原型、合規查核、流程／產能設計，以及前端與 AI 工具。

這些能力均有站內證據，不應要求訪客先讀完六張案例卡才自行歸納。首頁要主動完成這層翻譯。

### 1.3 她不只分析，也能交付可驗收成果

> 交付不只是一份建議，而是報表、查核表、規則、原型、儀表板或可操作 Demo。

這是 Zorya 與只做洞察或只做畫面的作品集之差異，也是招募者與客戶最值得在首屏記住的訊息。

### 現況問題

- `FDE × DATA SCIENTIST` 對熟悉職稱的人有效，對一般客戶不等於能力說明。
- 主標「把講不清楚的問題……」有記憶點，但缺少輸入、手段與輸出的具體名詞。
- 現有 pill「可承接需求釐清、原型、分析交付」資訊密度有限，且綠點的視覺語意偏向「目前可合作」，文案卻同時負責列能力，兩種任務互相稀釋。
- 三張數字 proof 證明成果，不能替代能力分類；訪客仍需推論「她到底會做什麼」。
- 手機版主標、說明、CTA、數字卡與 hero 圖依序堆疊，能力訊息沒有獨立層級，快速滑讀時更容易略過。

## 2. 建議方案與確切文案

### 2.1 Hero 資訊順序

桌機與手機均採同一語意順序：

1. eyebrow／角色
2. 理念主標
3. 具體副標
4. 「我能做什麼」能力帶
5. 合作狀態＋CTA
6. 成果數字
7. voxel hero 圖

能力帶必須在主要 CTA 之前，不能放到精選案例區之後；它是首屏定位資訊，不是第二區內容。

### 2.2 保留的 eyebrow

保留：

> FDE × DATA SCIENTIST

它負責職能標籤，不負責解釋服務。

### 2.3 保留的主標

保留現行主標與品牌藍強調：

> 把講不清楚的問題，  
> 變成能決策、能驗收的  
> 交付物。

主標是品牌承諾，不需塞入完整技能清單。桌機可沿用目前斷行；手機讓文字自然形成 3 行，不以額外 `<br>` 強迫出現孤字。

### 2.4 新的具體副標

以此句取代目前 lede：

> 從訪談、資料與流程找出真正卡點，交付可重算的分析、可操作的原型與可追蹤的系統。

此句明確交代：

- 輸入：訪談、資料、流程
- 核心工作：找出真正卡點
- 輸出：分析、原型、系統
- 品質條件：可重算、可操作、可追蹤

### 2.5 能力帶：確切文案與證據連結

區塊標籤：

> 我能做什麼

每項顯示「動詞短語＋箭頭」，整張項目皆可點擊；短語均不超過 12 個中文字／字元。`aria-label` 補上完整證據名稱，不把長說明塞進畫面。

| 顯示文案 | 主要證據連結 | `aria-label` 建議 | 證據依據 |
|---|---|---|---|
| 釐清需求與驗收 → | `cases/nutrition-liff/` | 查看需求釐清案例：營養諮詢飲食紀錄 LIFF | 從一句需求問出五個分歧、範圍與驗收條件 |
| 整併資料找異常 → | `cases/frozen-food/` | 查看資料異常案例：冷凍食品沖帳診斷 | 三來源整併、異常量化與 ROI 試算 |
| 建立規則型原型 → | `cases/trip-pricing/` | 查看規則原型案例：旅遊行程估價 | 規則引擎、7 個缺口、13 條驗收條件 |
| 查核合規風險 → | `cases/label-compliance/` | 查看合規查核案例：包裝標示改版 | 查核表、標示改版與風險損失試算 |
| 設計流程與產能 → | `cases/video-production/` | 查看流程設計案例：多門市影片產線 | 產線設計、成本模型與規模化排程 |
| 打造前端與 AI 工具 → | `demos/ai-service/` | 操作 Demo：電商 AI 客服 | 可操作對話介面、即時回覆與語音功能 |

補充證據：婚後財產案例可支撐「整併資料找異常／追溯」，ESG、點餐、輪盤與直播助手 Demo 可支撐「打造前端與 AI 工具」；首屏每項只放一個最直接入口，避免一項多連結造成選擇負擔。完整作品仍由案例與 Demo 索引承接。

### 2.6 Availability pill 升級

改為單一狀態訊息：

> 可承接專案合作

- 保留綠點，讓「可合作」語意與狀態燈一致。
- 移到能力帶之後、CTA 同一列之前或左側。
- 不再於 pill 內列「需求釐清、原型、分析交付」，避免和能力帶重複。
- 若目前並非開放接案，整個 pill 隱藏，不改成模糊的能力標籤。

### 2.7 CTA 文案

主要 CTA：

> 看代表案例 ↓

次要 CTA：

> 帶著問題來聊 →

主要 CTA 指向 `#featured-works`；次要 CTA 指向 `#contact`。移除主要 CTA 中的數字「3 個」，避免首頁日後調整精選數量時文案失準。

## 3. 版面、字級、token 與間距

### 3.1 共通原則

- 沿用現有 `1200px` 容器、7:5 hero 雙欄、卡片半徑與色彩 token。
- 不新增另一種品牌色；文字、邊界、hover 全部使用現有 CSS variables。
- 能力帶置於 `.hero3-copy`，不跨到右側圖片欄，確保閱讀順序穩定。
- 所有能力項目最小點擊區高 `44px`，鍵盤 focus 必須清楚。

### 3.2 桌機（1440px viewport）

Hero 維持兩欄：

| 項目 | 規格 |
|---|---|
| 外層 | `.wrap` 最大寬 `1200px`、左右 padding `32px` |
| 欄位 | `minmax(0, 7fr) minmax(0, 5fr)`、gap `24px` |
| hero 上／下 padding | `40px / 24px`；可由目前上方 `48px` 收至 `40px` 騰出能力帶空間 |
| eyebrow | `13px / 1.4`、字重 `600`、`letter-spacing: .08em`、`var(--accent-ink)` |
| 主標 | `clamp(40px, 4.6vw, 66px)`、行高 `1.14`、字距 `-.02em`、`var(--font-serif)` |
| 副標 | `17px / 1.7`、最大寬 `38ch`、`var(--ink-secondary)` |
| 能力區標籤 | `12px / 1.4`、字重 `700`、字距 `.08em`、`var(--ink-muted)` |
| 能力網格 | 2 欄 × 3 列、gap `8px 10px`、上距 `10px` |
| 能力項目 | 高度至少 `44px`、padding `9px 12px`、字級 `14px`、字重 `600` |
| 狀態／CTA 列 | 能力帶後 `20px`；元素間 gap `16px` |
| proof | CTA 後 `24px`；卡片間 gap `10px` |

能力項目樣式：

- 背景：`var(--surface-card)`
- 邊框：`1px solid var(--gridline)`
- 圓角：`8px`
- 文字：`var(--ink-primary)`
- 箭頭：`var(--accent-ink)`
- hover：邊框改為 `var(--accent)`，整體 `translateY(-2px)`
- focus-visible：`2px solid var(--accent)`，`outline-offset: 2px`
- 不使用陰影，避免六個小項目與成果卡、hero 圖爭奪層級

建議新增語意 token（定義在 `.home` 範圍，值仍引用全站 token）：

```css
.home {
  --cap-bg: var(--surface-card);
  --cap-border: var(--gridline);
  --cap-text: var(--ink-primary);
  --cap-action: var(--accent-ink);
  --cap-gap: 8px;
}
```

這些 alias 只為能力帶命名，不另造色值，深色模式可自動沿用現有 token。

### 3.3 手機（390px viewport）

手機優先順序是「角色 → 承諾 → 具體能力 → 行動」，不要求 hero 圖在第一屏完整露出。

| 項目 | 規格 |
|---|---|
| 外層 | 左右 padding `18px` |
| hero padding | 上 `28px`、下 `8px` |
| 主標 | `clamp(32px, 8.7vw, 38px)`、行高 `1.18`；禁止出現單一「的」成行 |
| 主標上距 | eyebrow 後 `14px` |
| 副標 | 主標後 `16px`；`16px / 1.65`；全寬 |
| 能力區 | 副標後 `18px` |
| 能力網格 | 2 欄 × 3 列、gap `8px` |
| 能力項目 | 最小高 `44px`、padding `8px 10px`、`13px / 1.35` |
| 狀態 pill | 能力帶後 `16px`；`12px`；高度至少 `32px` |
| CTA | 狀態後 `16px`；主按鈕與文字連結同列，可換行但不得小於 `44px` 點擊高 |
| proof | CTA 後 `24px`；2 欄排列，第三張落下一列，不壓縮字級 |
| hero 圖 | proof 後 `24px`，維持 3:2，不裁切、不另做小圖 |

手機首屏高度會因瀏覽器工具列不同而變化；驗收基準不是「圖片一定露出」，而是 **390 × 844 截圖中，六項能力、合作狀態與至少主要 CTA 均可見**。若超出，依序處理：

1. 將主標上／下空隙各減 `2–4px`。
2. 將能力項目垂直 padding 降至 `7px`，但點擊區仍以 `min-height:44px` 維持。
3. 將 proof 移到 hero 圖之後。

不得以縮小主標至 30px 以下、縮小正文至 15px 以下，或只顯示前三項能力解決高度問題。

### 3.4 建議 DOM 結構

```html
<p class="hero3-lede">…</p>
<nav class="capabilities" aria-label="我能做什麼">
  <span class="capabilities-label">我能做什麼</span>
  <div class="capabilities-grid">
    <a class="capability" href="cases/nutrition-liff/">釐清需求與驗收 <span aria-hidden="true">→</span></a>
    <!-- 其餘五項同表格 -->
  </div>
</nav>
```

用 `<nav>` 表示一組前往能力證據的導覽；不要用不可互動的 `<div>` 假裝按鈕。箭頭設為 `aria-hidden="true"`，完整目的由 `aria-label` 提供。

## 4. 圖示與 voxel 使用規則

### 建議：能力帶不使用 voxel 小圖示

能力項目只有約 44px 高。依 `VOXEL_STYLE_GUIDE.md`，voxel 圖仰賴小方塊、固定等角視角、漂浮底座與柔影；縮到 16–24px 後，這些特徵會糊成雜訊，也無法維持「一張圖一個隱喻」。六個縮圖還會搶走動詞短語的掃讀焦點。

因此能力帶採 **純文字＋單一箭頭符號 `→`**：

- 箭頭是導航提示，不是裝飾插畫。
- 可直接使用文字字元，無需 icon font、圖片資產或新的圖示套件。
- 若實作時必須使用圖形箭頭，採 12–14px 的 inline SVG，`stroke="currentColor"`、`fill="none"`，並設 `aria-hidden="true"`。
- 不建議用 CSS 畫六種不同圖示；辨識成本高於文字，也容易產生風格不一致。

### 保留 voxel 的位置

現有 hero voxel 圖完整保留，繼續作為「混亂經過路徑成為交付物」的視覺隱喻。任何未來替換圖仍須遵守 `VOXEL_STYLE_GUIDE.md`：固定等角視角、方形漂浮底座、暖白背景、品牌藍主角與最多一個琥珀異常點。

## 5. 刪除／保留清單

### 保留

- `FDE × DATA SCIENTIST` eyebrow。
- 理念主標與「能驗收」品牌藍強調。
- 7:5 桌機雙欄及手機單欄閱讀順序。
- 現有 hero voxel 圖、邊框、圓角與柔影。
- 主要／次要 CTA 的兩層行動架構。
- 三張成果 proof 的數據與卡片形式。
- 「先看成果，再看怎麼做到」以下的案例、流程與 Demo 章節。
- 深色模式、reduced motion、鍵盤 focus 等既有可及性行為。

### 取代

- 現有 lede「客戶說的需求，往往不是真正該解決的問題……」改為 §2.4 的具體副標。
- 現有 pill「可承接需求釐清、原型、分析交付」改為「可承接專案合作」。
- 主要 CTA「看 3 個代表案例 ↓」改為「看代表案例 ↓」。
- 次要 CTA「直接談需求 →」改為「帶著問題來聊 →」。

### 新增

- 副標下方的「我能做什麼」六項能力帶。
- 每一項對應的站內案例／Demo 深連結與完整 `aria-label`。

### 刪除／避免

- 刪除 hero 原 lede，不與新副標並存。
- 不再用 availability pill 羅列能力。
- 不新增「Data Analysis／AI／Frontend」等無證據、無動詞的 tag cloud。
- 不在能力帶加 voxel 縮圖、emoji、彩色 icon 或額外品牌色。
- 不把六項能力藏在輪播、accordion、hover tooltip 或漢堡選單裡。
- 不新增第四張 proof；能力清楚度不靠堆更多數字。
- 不改 hero 主圖、不重畫案例封面、不更動首屏以外的內容架構。

## 6. 驗收標準

### 6.1 內容與功能

- [ ] 首屏可直接讀到六項能力，且每項都是動詞短語、字面不超過 12 字元。
- [ ] 六項皆可點擊，目的地分別是指定案例或 Demo，無 404、無錯誤錨點。
- [ ] 新副標完整出現，沒有與舊 lede 重複。
- [ ] 綠點只對應「可承接專案合作」狀態。
- [ ] 鍵盤可依視覺順序走過六項能力、主要 CTA、次要 CTA；focus 樣式清楚。
- [ ] 深色與淺色模式均只使用現有色彩 token，文字與邊界可辨識。
- [ ] 關閉動畫或使用 `prefers-reduced-motion` 時，不影響能力內容出現。

### 6.2 1440 首屏測試

測試 viewport：`1440 × 900`，頁面載入後不捲動。

- [ ] 受測者 5 秒後能回答至少三類能力；合格答案需包含「需求／資料／原型或工具」三個不同面向，不能只回答「解決問題」。
- [ ] 受測者能指出至少一種交付物，例如分析、原型、系統、報表或儀表板。
- [ ] 六項能力、合作狀態、兩個 CTA 與三張 proof 均在首屏可見。
- [ ] hero 圖仍可見完整主要隱喻，文案欄與圖片欄沒有重疊。
- [ ] 能力帶不比主標搶眼；第一視線順序仍是主標 → 具體副標 → 能力。

### 6.3 390 首屏測試

測試 viewport：`390 × 844`，頁面載入後不捲動。

- [ ] 受測者 5 秒後能回答至少三類能力，且不需打開選單或滑動輪播。
- [ ] 六項能力、合作狀態與主要 CTA 均在首屏內；hero 圖可在第二屏開始出現。
- [ ] 主標沒有單一「的」或單一標點獨占一行。
- [ ] 能力帶為 2 欄 × 3 列；無橫向捲動、截字或碰撞。
- [ ] 每個能力連結與 CTA 的可點擊高度至少 `44px`。
- [ ] 200% 文字縮放後仍可閱讀與操作；允許項目增高，不得裁切文字。

### 6.4 5 秒測試話術與通過門檻

對未看過網站的招募者與潛在客戶各至少 3 人，隨機展示桌機或手機首屏 5 秒，關閉畫面後只問：

1. 「這個人能幫你做什麼？」
2. 「她交付的是建議，還是可以實際使用／驗收的東西？」

通過門檻：

- 6 人中至少 5 人能說出三類以上具體能力。
- 6 人中至少 5 人能回答「有可操作或可驗收的交付物」。
- 沒有人只留下「很會把事情講清楚」而說不出實際工作內容。

若未通過，優先調整能力短語與副標，不先放大圖示或增加裝飾。
